## Verified architecture and interaction patterns

### Desktop application

- The checked-out application is a Kotlin Multiplatform/Compose project with separate `desktop/app`, shared application/resources/configuration, and downloader/monitor modules (`settings.gradle.kts`, `desktop/app/build.gradle.kts`). The desktop binary has separate GUI, CLI, and Native Messaging entry points.
- UI components use state flows and component boundaries; the desktop home page composes a toolbar, category/queue sidebar, sortable download table, dialogs, and a footer with active-count and aggregate speed. The table supports selection, context menus, double-click detail opening, keyboard selection, drag/drop, configurable columns, status/progress, file size, speed, remaining time, and dates (`HomePage.kt`, `DownloadList.kt`, `TableDownloadItem.kt`). The inspected checked-in screenshots show the dense table and separate download-details/add-download windows; they are reference material only.
- The add-download dialog inspects the URL, shows detected file type/size and resume support, lets the user edit destination and filename, select a category/queue, open advanced configuration, and choose Add-to-queue or Download. Duplicate targets have explicit policies and error/validation states (`AddDownloadPage.kt`).
- Queues persist name, ordered item IDs, maximum concurrency, schedule windows, and stop-on-empty (`DownloadQueuePersistedDataAccess.kt`). Queue code starts work up to the concurrency limit, resumes queued items after completion, supports reorder/move and scheduled start/stop (`DownloadQueue.kt`, `QueuesPage.kt`, `ScheduleTimes.kt`). These behaviors were confirmed in code, not by running the AB application.
- Settings are grouped into Appearance, Download Engine, and Browser Integration. The source exposes theme/light-dark selection, UI scale, fonts, system tray, notifications, default folder, units, connection/thread count, max concurrency, retries, speed limit, dynamic segmentation, proxy, DNS, user-agent, and SSL-related controls. Settings use persistent stores (`DesktopSettingsComponent.kt`, `CommonSettings.kt`, `AppSettingsStorage.kt`). The README claims multiple themes and cross-platform support; this is project documentation, not independent verification of each platform.
- The checked-in colors/screenshots favor a dark, compact, high-density desktop layout with subtle selection/highlight accents. Useful patterns are the information hierarchy, configurable columns, always-visible throughput/ETA, deliberate empty/category filters, and separate task dialogs. ZEX's design below should use its own palette, spacing, icons, and branding.

### Browser extension and native integration

- The extension uses Vite/TypeScript and emits separate Manifest V3 Chrome and Manifest V2 Firefox builds (`package.json`, `manifest.chrome.ts`, `manifest.firefox.ts`). It combines browser action, content-script affordances, context menus, request/download observation, a settings/options page, and a Native Messaging/HTTP backend abstraction.
- The extension source uses `webRequest`, `cookies`, broad host permissions, and can forward request headers/cookies to the desktop app (`manifest/shared.ts`, `DownloadLinkInterceptor.ts`, `background/actions.ts`). AB's README describes automatic capture; the source applies file-type, size, blacklist, and shortcut filters. This is materially broader than ZEX's privacy-first explicit URL handoff, so ZEX will not copy those permissions or cookie forwarding without an explicit product/security decision.
- Native Messaging uses framed JSON, request IDs, typed actions (`ping`, `add`), a pending-request map with a timeout, and a fallback one-shot request when no persistent port is open (`NativeMessagingProtocol.ts`, `NativeMessagingTransport.ts`, desktop `StdioProtocol.kt` and `DefinedHandlers.kt`). The host forwards add requests through an app IPC service. Its framing uses a four-byte native-endian length; Native Messaging is platform-local and this is the standard representation on the Windows x64 target.
